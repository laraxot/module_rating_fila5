# Story Rating/5.152 — Select required

## Perché

Istruzione diretta dell'utente 2026-09-16: "il select deve essere obbligatorio, se
selezioni altro deve essere obbligatoria la textarea". La seconda metà è già
implementata e corretta (`Textarea::required(fn (Get $get) => self::selectIsOther($get($field)))`).
La prima metà no: in `HasRatingsTrait::buildRatingComponent()` il `Select` ha
`->nullable()` e un `//->required()` commentato, mai attivato — un requisito noto ma
dimenticato, non un'omissione di design.

Coerente con `CompilaIndennitaResponsabilita::ensureMinimumPositiveRatings()`, che già
impone un minimo di criteri valorizzati: un criterio con figli che resta senza risposta
non dovrebbe essere permesso silenziosamente a livello di singolo campo.

## Cosa cambiare

```php
$select = Select::make($field)
    ->options($options)
    ->hiddenLabel()
    ->validationAttribute($validationAttribute)
    ->placeholder(trans('rating::fields.scegli'))
    ->live()
    ->required()               // attivare, era commentato
    // ->nullable()             // rimuovere: in tensione con required()
    ->rules((string) ($rating->rule->value ?? ''))
    ->afterStateUpdated($afterStateUpdated);
```

**Tensione `nullable()` vs `required()`**: `nullable()` aggiunge tipicamente la regola
`nullable` (permette vuoto), `required()` aggiunge `required` (vieta vuoto) — insieme
danno un set di regole Laravel contraddittorio (`nullable|required`), dove `nullable`
di norma fa saltare le regole successive se il campo è vuoto, rendendo `required` di
fatto inefficace. Rimuovere `nullable()` quando si attiva `required()`, non tenerli
entrambi "per sicurezza".

**Nota**: verificare se `->placeholder()` resta compatibile con `->required()` — un
Select required con placeholder ma senza valore iniziale deve comunque bloccare il
submit finché non si sceglie un'opzione reale (figlio o «altro»), il placeholder è solo
testo guida, non un'opzione selezionabile.

## Acceptance criteria

- [ ] `Select::required()` attivo, `nullable()` rimosso
- [ ] Pest: verificare lo stato "required" del componente costruito (stesso approccio
      già usato in questa storia per `selectIsOther`/`getPlaceholder` — leggere la
      property interna via Reflection se `isRequired()` richiede container Filament
      live, come già documentato per la Textarea in 5.99)
- [ ] Nessuna regressione: Textarea resta required solo su «altro», sempre visibile
- [ ] `ensureMinimumPositiveRatings()` (IR) invariato — non duplica questa regola, resta
      dominio suo (soglia minima aggregata, non per-campo)
- [ ] PHPStan + Pint + PHPMD + PHPInsights verdi

## Fuori scope

- Cambiare `ensureMinimumPositiveRatings()` — resta IR-specifico
- Il comportamento «altro»/note — già corretto, non toccare

## Nota di processo

Codice commentato con un requisito noto ma mai attivato (`//->required()`) è un pattern
da tenere d'occhio: la regola era già scritta a metà, solo disattivata — non è stata
dimenticata dal design, è stata dimenticata l'attivazione. Vale la pena, quando si trova
un `//->qualcosa()` isolato senza spiegazione nel diff della stessa sessione, chiedersi
se sia un requisito a metà prima di ignorarlo come "codice morto".
