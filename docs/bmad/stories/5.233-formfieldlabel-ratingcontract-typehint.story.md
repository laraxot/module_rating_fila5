# 5.233 — `formFieldLabel(RatingContract $rating)`: type-hint sul contratto

## Perche' (ordine PO diretto)

> "piuttosto di `public static function formFieldLabel(BaseRating $rating)`
> avrei fatto `public static function formFieldLabel(RatingContract $rating)`"

## Fatto

- `RatingData::formFieldLabel` ora riceve `RatingContract $rating`:
  ```php
  public static function formFieldLabel(RatingContract $rating): string
  {
      return strip_tags((string) ($rating->txt ?? $rating->title));
  }
  ```
- Usato da `DecoratesRatingFormFields`, da
  `RatingData::criteriaToXlsFields` e da `HasRatingsTrait` interna
  (`self::` host → `RatingData::`).

## Perche' il contratto e non la classe base

1. La firma dice **cosa serve** (un criterio valutativo tipizzato) non **cosa e'**
   (la concreta `BaseRating` dei soli rating del modulo Rating).
2. Consumo cross-module: `IndennitaResponsabilita\Rating`, `Ptv\Rating` ecc.
   implementano `RatingContract` anche senza estendere `BaseRating`.
3. Accordo con la 5.232: **sia il check sia il type-hint** puntano al contratto —
   coerenza totale tra i due punti in cui il rating entra in `RatingData`.
4. `BaseRating` resta solo dove e' davvero la concreta (query, `relation`),
   mai dove il rating e' gia' un valore di dominio in input.
