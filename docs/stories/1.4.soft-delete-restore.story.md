# 1.4: Soft-delete + Restore Within 30 Days

**Story ID:** 1.4
**Epic:** 1 — Scheda Management Workflows
**Slug:** soft-delete-restore
**Status:** backlog

## Story

As an evaluator or HR admin,
I want to restore a soft-deleted Scheda within a 30-day grace period, and have older trashed records purged automatically,
so that accidental deletions are recoverable without keeping stale data indefinitely.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Deleting a Scheda (any status) from Filament sets `deleted_at` rather than removing the database row.
2. A soft-deleted Scheda no longer appears in the default `SchedaResource` list but is visible under a "Trashed" filter.
3. Evaluator/hr_admin can restore a soft-deleted Scheda within 30 days of `deleted_at`, clearing `deleted_at` and preserving its prior `status`.
4. A restore attempt on a Scheda whose `deleted_at` is more than 30 days in the past is rejected; no restore action is offered.
5. A scheduled command permanently deletes Scheda records soft-deleted more than 30 days ago, running daily.

## Tasks / Subtasks

- [ ] Confirm `deleted_at` column exists on `schedas` (added in Story 1.1's migration); add a follow-up migration only if missing (AC: #1)
- [ ] Add a "Trashed" table filter (`withTrashed`/`onlyTrashed`) to `SchedaResource` (AC: #2)
- [ ] Create `RestoreSchedaAction` enforcing `deleted_at >= now()->subDays(30)` before allowing restore (AC: #3, #4)
- [ ] Add a "Restore" row action, visible only for trashed records within the 30-day window (AC: #3, #4)
- [ ] Create `PurgeExpiredSchedaCommand` (artisan command) hard-deleting trashed records older than 30 days (AC: #5)
- [ ] Register the command on the scheduler to run daily (AC: #5)
- [ ] Feature tests: delete sets `deleted_at`; trashed filter shows/hides correctly; restore within window succeeds; restore past window blocked; purge removes only qualifying records (AC: #1-#5)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- [Source: prd.md#FR-001] "Soft delete (restore within 30 days)" acceptance criterion.
- [Source: prd.md#NFR-SEC-001] GDPR: "Right to erasure: soft-delete Scheda with 30-day grace (hard-delete on request)" — confirms the 30-day figure.
- [Source: architecture.md#data-model] `Scheda` entity constraint list explicitly includes "soft delete."
- [Source: architecture.md#adr-005] scheduled commands are the established pattern for background/archive-style work; the purge command follows the same pattern used for `ArchiveActivityLogs`.
- [Inference] NFR-SEC-001's "hard-delete on request" describes an immediate GDPR erasure-on-request flow that bypasses the 30-day window; that flow is out of scope for this story (belongs to Epic 3/4 GDPR work). This story implements only the standard 30-day soft-delete → restore → auto-purge cycle.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Unit:** `RestoreSchedaAction` rejects restore when `deleted_at` is older than 30 days; document the boundary assumption (day 30 still restorable, day 31 not).
- **Feature:** soft-delete via Filament delete action leaves the row in the DB with `deleted_at` set; Trashed filter toggling behaves correctly; Restore action visibility matches the 30-day rule; running the purge command via the test harness deletes only qualifying rows and leaves recently-trashed rows untouched.
- **Fixtures:** `SchedaFactory` states `trashedRecently()` (`deleted_at = now()->subDays(5)`) and `trashedExpired()` (`deleted_at = now()->subDays(31)`).
- **Edge cases:** restoring a record whose prior status was `submitted` returns it with `status = submitted` unchanged (only `deleted_at` is touched by delete/restore).
