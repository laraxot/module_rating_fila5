# 1.8: Edit Submitted Scheda (Audit Trail)

**Story ID:** 1.8
**Epic:** 1 — Scheda Management Workflows
**Slug:** edit-submitted-audit-trail
**Status:** backlog

## Story

As an evaluator or HR admin,
I want to correct a submitted or approved Scheda through a controlled flow that records every change,
so that necessary corrections remain possible without losing accountability.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Evaluator/hr_admin can edit a Scheda whose status is `submitted` or `approved` through a distinct "Edit submitted" flow, separate from the draft-only edit form guarded in Story 1.3.
2. Each field change (old value, new value, field name) made through this flow is captured and persisted as an audit entry associated with the Scheda, the acting user, and a timestamp.
3. The audit entries are visible on the Scheda detail view as a chronological change log.
4. A Scheda's `status` is not altered by this edit flow (editing submitted content does not revert it to draft).
5. Only evaluator/hr_admin roles can use this flow; staff cannot edit any Scheda at any status.

## Tasks / Subtasks

- [ ] Create `SchedaObserver` (or a dedicated `UpdateSubmittedSchedaAction`) capturing field-level diffs on update when `status != draft` (AC: #2)
- [ ] Persist diffs via the Activity module's write contract (Epic 4, story 4.1) (AC: #2)
- [ ] Add an "Edit submitted" Filament action/page enabling field edits when `status` is `submitted` or `approved` (AC: #1, #4)
- [ ] Display the change log (Activity entries for this Scheda) on the detail/view page (AC: #3)
- [ ] Gate the flow behind an evaluator/hr_admin policy (AC: #5)
- [ ] Feature tests: edit captures diff entries; status unchanged after edit; change log renders entries in order; staff role denied (AC: #1-#5)

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Unit:** diff-capture logic produces correct old/new value pairs for a multi-field update (e.g., two scores changed in one save).
- **Feature:** editing a submitted Scheda's score persists the new value and creates matching Activity entries (document whether one entry per changed field or one structured-diff entry, matching 4.1's contract shape); `status` remains `submitted` after edit; change log UI lists entries newest-first; a staff-role user attempting the edit flow is denied.
- **Fixtures:** `SchedaFactory` `submitted()` state; an authenticated evaluator user factory.
- **Edge cases:** saving with no actual field changes creates no audit entry; two sequential edits each produce their own audit entry rather than overwriting the prior one.
