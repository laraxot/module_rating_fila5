# 1.9: Approval Workflow (Manager Sign-off)

**Story ID:** 1.9
**Epic:** 1 — Scheda Management Workflows
**Slug:** approval-workflow-signoff
**Status:** backlog

## Story

As a manager,
I want to approve a submitted Scheda (or have the employee raise an appeal if they dispute it),
so that finalized evaluations are formally signed off with an accountable approver.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A manager/senior-approval role user can approve a Scheda whose status is `submitted`, setting `status = approved` and `approved_at` to the current timestamp.
2. Approval is only available on submitted records; draft records show no approve action.
3. If the employee disputes the evaluation, an `Appeal` record (`employee_id`, `scheda_id`, `reason`, `status = pending`) can be created and is visible in the Progressioni module's resource list.
4. Only users with the manager/senior-approval role can approve; the evaluator who created the Scheda cannot approve their own submission.
5. Approving a Scheda emits an approval event (approver name, timestamp) for Epic 4's Activity log to consume.

## Tasks / Subtasks

- [ ] Create `ApproveSchedaAction` transitioning submitted → approved, setting `approved_at`, blocking self-approval by comparing approver to the creating evaluator (AC: #1, #2, #4)
- [ ] Add an "Approve" Filament action on `SchedaResource`, visible only when `status = submitted` (AC: #1, #2)
- [ ] Create `Appeal` model (`Modules/Progressioni`) with `employee_id`, `scheda_id`, `reason`, `status` (AC: #3)
- [ ] Create a minimal `ProgressioniResource` Filament resource listing `Appeal` records (AC: #3)
- [ ] Add a "Raise appeal" action on the Scheda detail view creating an `Appeal` record (AC: #3)
- [ ] Gate the approve action behind a manager/senior-approval policy distinct from the general evaluator policy (AC: #4)
- [ ] Emit an approval event/log call for Epic 4 to consume (AC: #5)
- [ ] Feature tests: approve transitions status/sets `approved_at`; approve hidden on draft; self-approval blocked; appeal creation visible in `ProgressioniResource` (AC: #1-#5)

## Dev Notes

- [Source: architecture.md#data-model] `ProgressioniApproval` is a separate entity for career-progression approvals (FR-009 scope); this story's Scheda approval is a distinct, simpler transition using Scheda's own `status`/`approved_at` columns, not `ProgressioniApproval`.
- [Inference] architecture.md's Data Model table does not list an `Appeal` entity. This story introduces a minimal `Appeal` model sized to (`employee_id`, `scheda_id`, `reason`, `status`) as the seed for NFR-REG-001's "Appeal logging" requirement. Full resolution workflow and Activity-table integration are completed by Epic 4 story 4.3, per docs/context/sharding-context.md's explicit note that `Modules/Progressioni/app/Models/Appeal.php` is "shared with Epic 1; coordinate via dependency map."
- [Source: prd.md#NFR-REG-001] "Appeal logging: log all appeals in Activity table with resolution" — confirms appeals are an in-scope compliance requirement, split across Epic 1 (creation, this story) and Epic 4 (resolution/audit, story 4.3).
- [Source: architecture.md#adr-004] policies gate every resource action; self-approval prevention is an explicit authorization rule, not merely a UI hide.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Feature:** approve a submitted Scheda → status becomes `approved`, `approved_at` set; approve action absent for draft records; approval attempt by the same user who created/submitted the Scheda is rejected; a non-manager role cannot see/trigger approve.
- **Feature:** raising an appeal creates an `Appeal` row visible in `ProgressioniResource`'s list with `status = pending`.
- **Fixtures:** `SchedaFactory` `submitted()` state with a distinct "creator" user vs. "approver" user; `Appeal` factory.
- **Edge cases:** approving an already-approved record is a no-op/action hidden; document whether an appeal can be raised on a not-yet-submitted (draft) Scheda — this story's default assumption is "allowed" (disputes can precede submission), the dev agent implements accordingly and notes the decision.
