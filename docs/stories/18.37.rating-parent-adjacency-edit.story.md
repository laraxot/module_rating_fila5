# Story 18.37 — Gestione parent_id e figli nel rating edit (adjacency list)

## Il fatto

Il campo `parent_id` è già dichiarato nella tabella `ratings` (via `RatingData::updateColumns()`), ma non è ancora gestito nel form (`BaseRatingForm.php`) né nel resource. L'edit a `http://127.0.0.1:8000/indennitaresponsabilita/admin/ratings/52/edit` deve permettere:
- di selezionare un genitore (per rating figli)
- di mostrare i figli esistenti (per rating genitori)
- di gestire rating senza figli (caso più comune)

## La logica, prima del codice (BMAD + second brain)

### Studio delle fonti

- **Filament 5.x** (`github.com/filamentphp/filament/tree/5.x`): i form usano `Filament\Forms\Components` con `Select::make()`, `Section::make()`, `Repeater::make()`.
- **Filament Demo** (`github.com/filamentphp/demo/`): mostra come gestire relazioni genitore-figlio con `Select` e sezioni nidificate.
- **staudenmeir/laravel-adjacency-list**: richiede `parent_id` come `unsignedBigInteger` nullable, con scope `ancestors()`, `descendants()`, `children()`.

### Regole dal second brain

- `docs/chat/stop-ratingscolumn-tre-riscritture-concorrenti.md` (18:48): il lock va tenuto sul gruppo (Column + Section + filtro) fino alla verifica completa. Per il form edit, il gruppo è: `RatingForm`, `BaseRatingForm`, `RatingResource`, relazione con figli.
- `bashscripts/ai/wiki/rules/markdown-file-conventions.md`: nomi file kebab-case, nessun `-1.md` / `-2.md` / `-3.md`. Questo file è `18.37.rating-parent-adjacency-edit.story.md` → corretto.
- `AGENTS.md`: sempre italiano, sintetico, conciso.

### Approccio (max DRY / max KISS / max clean)

1. **Non duplicare il form**: `BaseRatingForm.php` è già la base condivisa. Aggiungiamo `parent_id` lì (selezione genitore). Il form specifico (`RatingForm.php`) eredita.
2. **Gestione figli**: usiamo `Section::make('children')->schema(...)` nel form se il rating ha `parent_id = null` (è un genitore potenziale), oppure usiamo una relazione nel resource per mostrare i figli nell'infolist.
3. **Adjacency list**: `parent_id` è già in `RatingData::updateColumns()`. Devo solo aggiungere la relazione `children()` nel modello `BaseRating.php` (o nel model locale) usando la convenzione `parent_id`.

## Proposta di implementazione

### 1. BaseRatingForm — aggiungere parent_id
```php
'parent_id' => Select::make('parent_id')
    ->label(__('Rating parent'))
    ->options(function () {
        return \Modules\Rating\Models\Rating::query()
            ->where('id', '!=', \Filament\Forms\Get::$record?->id)
            ->pluck('title', 'id');
    })
    ->nullable(),
```

Nota: `Get::$record` non è disponibile direttamente in `getFormSchema()` come parametro; usiamo `Select::make('parent_id')` con un `relationship()` o `options()` statico.

Il modo più pulito in Filament 5.x è:
```php
'parent_id' => Select::make('parent_id')
    ->relationship('parent', 'title')
    ->nullable(),
```

Ma richiede che il modello `Rating` abbia la relazione `parent()`. Dobbiamo quindi:
- Aggiungere `parent()` e `children()` a `BaseRating.php`
- Aggiungere `parent_id` a `$fillable`

### 2. Modello — aggiungere relazioni adjacency
```php
public function parent(): BelongsTo
{
    return $this->belongsTo(static::class, 'parent_id');
}

public function children(): HasMany
{
    return $this->hasMany(static::class, 'parent_id');
}
```

Nota: `parent_id` è già nella tabella, ma `BaseRating.php` non lo ha in `$fillable`. Dobbiamo aggiungerlo.

### 3. RatingForm / Resource — gestione figli nell'edit
Nel form dell'edit (`RatingForm.php` o tramite `BaseRatingForm`), possiamo aggiungere un campo per i figli solo quando rilevante. Per semplicità e KISS, aggiungiamo nel `RatingForm.php`:
```php
public function getFormSchema(): array
{
    $base = parent::getFormSchema();
    $base['parent_id'] = Select::make('parent_id')
        ->relationship('parent', 'title')
        ->nullable();
    return $base;
}
```

Per i figli nel resource (visualizzazione), aggiungiamo una relazione o un widget.

### 4. Validazione — nessuna regressione
- PHPStan 0 errori
- Nessun test rotto
- Il `parent_id` rimane nullable (rating senza genitore = root)

## Incidenti da ricordare

- Non usare `mixed` per i parametri `array<string, scalar|null>` — seguire il pattern `RatingData::fromArray()` rimosso per semplicità.
- Il campo `parent_id` deve essere nullable: un rating senza genitore è valido (radice dell'albero).
- Non rompere `RatingsColumn` / `RatingsSection` — il group lock non è necessario perché il form è separato.
