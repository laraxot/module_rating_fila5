# Story 18.56: accessor `ratings_by_id` e `ratingValuePath()` in HasRatingsTrait

Status: done

## Story

As a manutentore di un host di `HasRatingsTrait` (export XLS, colonne, infolist),
I want leggere il valore pivot di un rating con un percorso `data_get` per id del rating,
so that nessun host debba sapere che la relazione e' indicizzata per posizione e che
`value` vive sul pivot, e nessuno riscriva il percorso a mano modulo per modulo.

## Il fatto misurato

Misura su tenant `local/ptvx` (DB 10.100.200.53, non produzione), 2026-09-22, riga
campione `SchedaDip` id 9166 (anno 2026, valutatore 580, 10 rating valorizzati):

| espressione | risultato |
|---|---|
| `$row->ratings->keys()` | `[0, 1, 2, ..., 9]` (posizione) |
| `$row->ratings->pluck('pivot.value', 'id')` | `{52: 57, 34: 1, 35: 1, ..., 42: 600}` |
| `data_get($row, 'ratings.52.value')` | `null` |
| `data_get($row, 'ratings.52.pivot.value')` | `null` |
| `data_get($row, 'ratings.0.pivot.value')` | `57` |
| `data_get($row->ratings->keyBy('id'), '52.pivot.value')` | `57` |

Due cause, non una:

1. `ratings()` e' una `MorphToMany` (`HasRatingsTrait.php` righe 78-93): la collection
   che ne esce e' una lista, chiave `0..n-1`. `ratings.52` chiede l'elemento in posizione
   52, che non esiste con 10 rating caricati. Con piu' di 52 rating caricati restituirebbe
   il rating sbagliato, in silenzio.
2. Il valore della valutazione sta sul pivot `rating_morph` (`$rating->pivot->value`), non
   su `ratings.value`. Il trait lo dice gia' nel docblock di `ratingMorphs()` (righe 61-63):
   `sum('ratings', 'value')` e' un errore SQL per lo stesso motivo.

La relazione e' caricata (`IndennitaResponsabilita::$with = ['ratings']`, riga 444): non
e' un problema di lazy loading. Il percorso e' sbagliato, non i dati.

## Perche' nel trait e non nell'host

`HasRatingsTrait::ratingFieldName()` (righe 297-308) e' gia' la convenzione unica del
percorso di form: `'ratings.'.$rating->id.'.pivot.'.$pivotColumn`. Il suo docblock dice il
perche': "se cambia, cambia in un posto solo". Il percorso di lettura via `data_get` e' la
controparte esatta e merita lo stesso trattamento: il componente porta la sua logica, chi
compone la chiede.

Alternative scartate (dossier di sessione, sezione 6):

- `keyBy('id')` dentro `CollectionExport` quando il campo inizia con `ratings.` (ADR-003
  del peer in `Ptv/docs/bmad/architecture/export-xls-base-list-schedas.md`): accoppia
  l'exporter generico di Xot al dominio Rating e resta ambiguo fra indice e id.
- Campi per indice `ratings.0.pivot.value`: dipende dall'ordine, si rompe al primo
  `ordered()` diverso.
- Accessor magico per singolo rating (`rating_52` via `__get`): magia non tipizzabile.
- Accessor sul solo model host (quello che esiste oggi in IR, vedi sotto): funziona per
  un modulo, va riscritto uguale in ogni altro host del trait (Performance, Progressioni,
  Ptv passano tutti da `BaseScheda`, che usa il trait alla riga 112).

## Snippet proposto

Da inserire in `HasRatingsTrait`, subito dopo `ratingFieldName()` (riga 308), cosi' le due
convenzioni del percorso stanno una accanto all'altra. Import gia' presenti nel file:
`Illuminate\Database\Eloquent\Collection as EloquentCollection`, `BaseRating`.

```php
/**
 * `ratings` indicizzata per id del rating, per `data_get()`.
 *
 * `ratings()` e' una MorphToMany: la collection e' una lista (chiavi 0..n-1), quindi
 * `data_get($host, 'ratings.52.pivot.value')` legge la posizione 52, non il rating 52,
 * e con meno di 53 righe caricate risponde `null` senza errore. Il valore sta sul
 * pivot: `ratings.{id}.value` e' sbagliato due volte. Nessuna query in piu': legge la
 * relazione gia' caricata (o la carica una volta sola, come ogni altro `$this->ratings`
 * del trait). Controparte di lettura di {@see ratingFieldName()}: il percorso lo
 * costruisce {@see ratingValuePath()}, mai a mano nell'host.
 *
 * @return EloquentCollection<int, BaseRating>
 */
public function getRatingsByIdAttribute(): EloquentCollection
{
    /** @var EloquentCollection<int, BaseRating> $byId */
    $byId = $this->ratings->keyBy('id');

    return $byId;
}

/**
 * Il percorso `data_get()` del valore pivot di un rating sull'host.
 *
 * Stessa convenzione unica di {@see ratingFieldName()}, ma per leggere lo stato
 * caricato invece che per nominare un campo di form: `ratings_by_id.{id}.pivot.{col}`.
 * `$pivotColumn` resta `'value'` per default; `'note'` e' l'altra colonna pivot che il
 * trait genera oggi. Statico perche' chi lo usa (es. `getXlsFields()`) non ha ancora
 * un'istanza dell'host: ha solo il rating.
 */
public static function ratingValuePath(BaseRating $rating, string $pivotColumn = 'value'): string
{
    return 'ratings_by_id.'.$rating->id.'.pivot.'.$pivotColumn;
}
```

Nota PHPStan: `Enumerable::keyBy()` (vendor, riga 543) dichiara `static<array-key, TValue>`
quando l'argomento e' una stringa. Senza il `@var` locale, a livello max il tipo di ritorno
`EloquentCollection<int, BaseRating>` non combacia. Il `@var` locale e' lo stile gia' usato
nel trait (`getMyRatingAttribute()`, `getRatingsWhere()`, `syncRatingsWhere()`). Se il
dev preferisce evitare l'annotazione, `keyBy(static fn (BaseRating $rating): int => (int) $rating->id)`
produce `static<int, BaseRating>` per costruzione; i test passano in entrambi i casi.

## Second brain

- Un percorso `data_get` su una relazione many-to-many non e' mai per id: la collection
  e' una lista. Se un host ha bisogno dell'id come chiave, il trait che possiede la
  relazione espone la vista indicizzata, non l'host.
- La controparte di un metodo che nomina un campo (`ratingFieldName`) e' un metodo che
  nomina un percorso di lettura (`ratingValuePath`). Se esiste il primo e manca il
  secondo, gli host lo riscrivono a mano (IR riga 139 oggi).
- Il dossier di sessione diceva "nomi liberi" per `ratings_by_id`: era vero a HEAD
  e034881852, falso da 7ba3feacd4 (17 minuti dopo). Il grep si rifa' al momento della
  scrittura, non si copia dal dossier.
