# Story 5.90 — La risoluzione giusta senza rete

## User story

Come manutentore di `Rating`, voglio che `resolveRatingClass()` sia difeso da un test e
spiegato nel suo docblock, perché oggi è corretto per caso: nessuno ha scritto perché, e
nessuno si accorgerebbe se tornasse indietro.

## Il fatto

`HasRatingsTrait` risolve in quattro punti la classe `Rating` del modulo host —
`ratingMorphs()`, `ratings()`, `ratingObjectives()`, `myRatings()`, `syncRatingsWhere()`.

| | |
|---|---|
| Versione **committata** (`b2d53b8`, unico commit sul file) | `$related = Rating::getClassName();` |
| Working tree, **non committato** | `$related = $this->resolveRatingClass();` |
| Test che coprono il risolutore | **nessuno** — `grep -rln resolveRatingClass tests/` è vuoto |
| Docblock | dice *cosa* fa, non *perché* non usa `getClassName()` |

La modifica è corretta. Ma è una correzione senza rete: sta nel working tree di un'altra
sessione, non è committata, non è testata e non è motivata.

## Le tre differenze, misurate

### 1. `getClassName()` legge il chiamante, non l'host

`XotBaseModel::getClassName()` ricava il namespace da `debug_backtrace()`: il primo frame con
un oggetto la cui classe contiene `Models\` o `Filament\Resources\`.

```
host = IndennitaResponsabilita, frame intermedio = Progressioni\Models\Scheda

  resolveRatingClass  ->  Modules\IndennitaResponsabilita\Models\Rating   (static::class)
  getClassName        ->  Modules\Progressioni\Models\Rating              ← sbagliata
```

Nessuna eccezione. La relazione punterebbe al `Rating` di un altro modulo, **su un'altra
connection**. È il difetto peggiore dei tre perché **non si vede**: un `ratings()` che
restituisce righe plausibili di un'altra tabella.

### 2. Fallback contro eccezione

Da un host in un modulo senza `Models\Rating` proprio (provato con
`Modules\Notify\Models\MailTemplate`):

```
getClassName        ->  LANCIA Webmozart\Assert\InvalidArgumentException
                        Expected an existing class name. Got: "Modules\Notify\Models\Rating"
resolveRatingClass  ->  fallback a Modules\Rating\Models\Rating
```

Conta perché `HasRatingsTrait` sta su `Ptv\Models\BaseScheda`, la base della piattaforma: la
prossima foglia che compone `BaseScheda` senza avere un `Rating` proprio si rompe **a
runtime**, non al deploy. Oggi tutti e 4 i moduli host ne hanno uno — `IndennitaResponsabilita`,
`IndennitaCondizioniLavoro`, `Progressioni`, `Ptv` — quindi il caso non è mai stato incontrato.

### 3. Costo

2000 iterazioni sullo stesso host:

| | ms |
|---|---:|
| `resolveRatingClass` | 33,5 |
| `getClassName` | 99,0 (**3x**) |

`ratings()` è un percorso caldo, e il baseline è perfino gonfiato dalla reflection del probe.

### Quarta differenza, oggi innocua

`resolveRatingClass()` verifica `is_subclass_of($moduleRatingClass, BaseRating::class)`;
`getClassName()` asserisce solo `EloquentModel`. Verificato che tutti e 6 i `Models\Rating` di
modulo sono sottoclassi di `BaseRating`, quindi la guardia non morde — ma è la rete che
impedisce a una classe sbagliata di arrivare all'`Assert::subclassOf` dentro `ratings()`.

## Perché `getClassName()` non è adatto **qui** (e altrove sì)

Il suo docblock dichiara lo scopo: risolvere il concreto del modulo chiamante **quando
`static::class` è fermo sul prototype del modulo base** — una `Scheda` di Progressioni che
invoca `Ptv\Models\CriteriOption::getClassName()`.

In un trait quel problema **non esiste**: il trait viene appiattito nella classe host, quindi
`static::class` **è già** l'host. `getClassName()` userebbe `debug_backtrace()` per ricostruire
un'informazione che il trait ha già, gratis e in modo deterministico.

Non è un difetto di `getClassName()`: è il posto sbagliato per usarlo.

## Acceptance criteria

- [ ] Il docblock di `resolveRatingClass()` dice **perché** non `getClassName()`: in un trait
      `static::class` è già l'host, e il chiamante non è una fonte affidabile
- [ ] Test: host con `Rating` di modulo → risolve quello del proprio modulo, per tutti e 4 i
      moduli host reali
- [ ] Test: host in un modulo **senza** `Models\Rating` → fallback a `Modules\Rating\Models\Rating`,
      **nessuna eccezione**
- [ ] Test: la risoluzione **non dipende dal chiamante** — con un frame intermedio di un altro
      model il risultato resta quello dell'host
- [ ] Test: un `Models\Rating` che non estende `BaseRating` non viene restituito (fallback)
- [ ] La modifica pendente è committata: oggi vive solo nel working tree
- [ ] `XotBaseModel::getClassName()` **non** viene toccato: è legittimo per il caso per cui è nato

## Cosa NON fa questa story

- Non tocca `getClassName()`. Se serve una nota nel suo docblock su *quando non usarlo*, è una
  decisione di `Xot` — vedi domanda 3 nella discussion.
- Non normalizza `rating_morph.model_type`: quello è `Rating/8.18`.
