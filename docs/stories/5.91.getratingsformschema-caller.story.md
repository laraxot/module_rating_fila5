## Filosofia / Zen / Perché / Religione

**Perché non lasciare `getRatingsSchema()` solo in `CompilaIndennitaResponsabilita`:**

Il trait `HasRatingsTrait` già possiede le relazioni Eloquent (`ratings()`, `ratingMorphs()`, `myRatings()`). La costruzione del form schema è un **concetto parallel** all'accesso ai dati: se il model conosce i rating, deve anche saperli presentare. Oggi `CompilaIndennitaResponsabilita` duplica implicitamente questa capacità (riesce a iterare `ratings`, leggere `is_readonly`, `rule`, `txt`, `title`, costruire `TextInput`/`TextEntry`). Spostare la logica generica nel trait è DRY; lasciare nel page solo i **calcoli specifici** (`getTot`, `getImportoMensileCalcolato`) è KISS.

**Perché `$caller`:**

`getRatingsFormSchema()` nel trait non può conoscere le formule del modulo chiamante (es. `Importo = tot * 10 * perc_p_time_year`). Il parametro `$caller` (istanza della page o un valore di configurazione) permette al trait di chiamare metodi aggiuntivi quando esistono: `recalculateReadonlyFields`, `getTot`, `getImportoMensileCalcolato`, ecc. Se il chiamante non fornisce quei metodi, il trait usa il fallback generico.

**Perché NON spostare i calcoli nel trait:**

Le formule (`*10.0`, `*12.0`, `*perc_p_time_year`) sono business logic di `IndennitaResponsabilita` (contractual, legale, retributiva). Non appartengono a `Rating` che è generico. Il trait deve offrire il **meccanismo** (recalculation hook, readonly detection, label formatting) non la **politica**.

## Visione / Scopo / Logica

- **Visione:** ogni module che usa `HasRatingsTrait` può generare la propria form per i rating senza duplicare il loop su `ratings`.
- **Scopo:** estrarre `getRatingsSchema()` in `HasRatingsTrait::getRatingsFormSchema($caller = null): array`.
- **Logica:** il metodo itera `$this->ratings`, crea `TextInput`/`TextEntry`, gestisce `is_readonly` e `rule`; se `$caller` è fornito e ha metodi di calcolo, attiva `afterStateUpdated` per recalculation.
- **Politica:** il trait non importa `Filamentorms/components` se non espressamente richiesto; ma `Rating` è un modulo di framework (usato da Filament), quindi è accettabile.
- **Religione / Zen:** "Il trait sa come chiedere, non come rispondere": offre lo schema, il chiamante offre la logica.

## Analisi della pagina sorgente (`CompilaIndennitaResponsabilita.php`)

### Comportamenti particolari che devono restare nel page (via `$caller`):

1. **Readonly fields con calcoli automatici** (`getTot`, `getImportoMensileCalcolato`, `getImportoMensileAttribuito`, `getImportoAnnualeAttribuito`). Questi usano `$get('ratings')`, iterano `valueFields` e applicano formule specifiche (`*10`, `*perc_p_time_year`, `*12`). Non devono andare nel trait.

2. **`recalculateReadonlyFields()`** — chiama metodi dinamici (`get` + studly title) sul `$this` della page. Se il trait deve supportarlo, deve chiamare su `$caller` (se fornito) o ignorare.

3. **Special formatting**: `Str::contains($label, 'Importo')` → `money('EUR')`. Questo è una regola di presentazione specifica del modulo. Potrebbe essere configurabile tramite `$caller` o un parametro opzionale.

4. **Validazione custom** (`MIN_POSITIVE_RATINGS` = 2): questa è business policy di `IndennitaResponsabilita`. Non va nel trait.

5. **`fillFormWithInitialData()`**: logica di inizializzazione dei dati con `pivot.value`. Potrebbe restare nel page.

### Cos'è generico e può andare nel trait:

- Loop su `$this->ratings` (relazione già nel trait)
- Creazione `TextInput::make('ratings.{id}.pivot.value')`
- Gestione `is_readonly` → `TextEntry` vs `TextInput`
- Layout `inlineLabel()`, `columns(2)`, `numeric()`, `nullable()`
- `label()` da `txt ?? title`
- `rules()` da `rating->rule->value`
- `live(onBlur: true)`
- `afterStateUpdated` che chiama `$caller->recalculateReadonlyFields()` se `method_exists()`

## Design del nuovo metodo (`HasRatingsTrait`)

```php
public function getRatingsFormSchema(?object $caller = null): array
{
    $ratings = $this->ratings; // relazione dal trait
    $schema = [];
    $readonlyFields = $ratings->where('is_readonly', true);

    foreach ($ratings as $rating) {
        $fieldname = 'ratings.' . $rating->id . '.pivot.value';
        $label = strip_tags((string) ($rating->txt ?? $rating->title));
        $readOnly = (bool) ($rating->is_readonly ?? false);

        if (! $readOnly) {
            $item = TextInput::make($fieldname)
                ->label($label)
                ->numeric()
                ->nullable()
                ->columns(2)
                ->inlineLabel()
                ->live(onBlur: true)
                ->rules((string) ($rating->rule?->value ?? ''));

            if ($caller && method_exists($caller, 'recalculateReadonlyFields')) {
                $item->afterStateUpdated(function (Set $set, Get $get) use ($caller, $readonlyFields): void {
                    $caller->recalculateReadonlyFields($set, $get, $readonlyFields);
                });
            }
        } else {
            $item = TextEntry::make($fieldname)
                ->label($label)
                ->inlineLabel()
                ->default(Arr::get($this->data ?? [], $fieldname, 0));

            if (Str::contains($label, 'Importo') && method_exists($item, 'money')) {
                $item->money('EUR'); // configurabile via $caller in futuro
            }
        }
        $schema[] = $item;
    }

    return $schema;
}
```

## Parametro `$caller` — specifiche

- Tipo: `?object` (istanza della page `CompilaIndennitaResponsabilita` o simile)
- Uso nel trait:
  1. Chiamare `recalculateReadonlyFields($set, $get, $readonlyFields)` se `method_exists($caller, 'recalculateReadonlyFields')`
  2. Chiamare calcoli (`getTot`, `getImportoMensileCalcolato` ecc.) se necessari per il form schema (oggi solo per `afterStateUpdated`)
  3. Permettere override di `label()` o `formatStateUsing()` tramite chiamata al chiamante
- Non è obbligatorio: `getRatingsFormSchema()` deve funzionare anche senza (`$caller = null`)

## Dev Notes / Guardrail

- Non tocca `XotBaseModel::getClassName()` — già dedicata a risolvere il classe del modulo chiamante per il model, non per il form.
- `Rating::getClassName()` è usato per la relazione; non confondere con il form schema.
- La relazione `ratings()` resta nel trait; il form schema è un'**estensione di presentazione**, non una relazione.
- `HasRatingsTrait` usa `@template TModel`; il form schema deve mantenere la coerenza tipo ma non è una relazione Eloquent.
- Non usare `Service` per questa logica: il trait è la sede corretta per la logica di presentazione dei rating, come già per le relazioni.

## Misure aggiunte il 2026-09-09 (sessione c21fdd4e) — e tre punti da correggere qui sopra

Questa story e' stata scritta prima di misurare. Le misure non la smentiscono nella
sostanza, ma spostano il **motivo** per cui vale la pena farla, e correggono tre
affermazioni.

### 1. «Ogni module che usa il trait puo' generare la propria form» — oggi il riuso non c'e'

13 pagine `Compila*` nel monorepo, **una sola** costruisce lo schema dei rating:

| pagina | righe | schema rating |
|---|---:|---|
| `IndennitaResponsabilita/.../CompilaIndennitaResponsabilita.php` | 427 | **si** |
| `Progressioni/.../CompilaScheda.php` | 212 | no |
| `IndennitaCondizioniLavoro/.../CompilaCondizioniLavoro.php` | 206 | no |
| altre 10 | 13-32 | no |

Il DRY fra moduli e' **prospettico**. Lo standing order dice «prima misura la
duplicazione, poi estrai»: qui la duplicazione e' uno.

### 2. «Rating e' un modulo di framework, quindi importare Filament e' accettabile»

Misurato: **nessun model del monorepo importa un componente form di Filament.** I sette
file sotto `app/Models` che importano da `Filament\` importano contratti
(`FilamentUser`, `HasTenants`, `HasAvatar`), `Panel`, la facade e una `Notification`.
Zero `Filament\Forms\Components\*`.

Non e' un veto: e' un **precedente** che questa story creerebbe, e che verra' citato.
Va deciso esplicitamente, non dato per acquisito. Le tre opzioni sono nella
[discussion #24](https://github.com/provtv/module_rating_fila5/discussions/24).

### 3. `RatingsSection` esiste gia', e questa story non lo cita

`Modules/Rating/app/Filament/Forms/Components/RatingsSection.php` — **di sola lettura
per scelta dichiarata**: «i voti non si scrivono da qui, si scrivono dove si valuta».
E' lo specchio di `RatingsColumn`. Quindi il pezzo mancante e' il suo **gemello
editabile**, e la regola `filament-form-components-vocabulary` indica gia' dove vivono
i blocchi di campi riutilizzabili.

### 4. Il motivo vero per estrarre: due sniff di stringa che falliscono in silenzio

| sniff | dove | effetto di una rinomina |
|---|---|---|
| `'get'.Str::studly($rating->title)` | `recalculateReadonlyFields()` | `method_exists` false: il campo calcolato smette di aggiornarsi, **nessun errore** |
| `Str::contains($label,'Importo')` -> `money('EUR')` | ramo readonly | il campo perde gli euro, **nessun errore** |

Sui dati reali (16 righe readonly, 4 gruppi anno/tipo):

| id | `title` (dispatch) | `txt` (label e money) | money | metodo atteso |
|---:|---|---|---|---|
| 9 | `tot` | `Totale Punti` | no | `getTot` |
| 10 | `importo mensile calcolato` | `Importo mensile calcolato` | si | `getImportoMensileCalcolato` |
| 11 | `importo mensile attribuito` | `Importo mensile attribuito` | si | `getImportoMensileAttribuito` |
| 12 | `importo annuale attribuito` | `Importo annuale attribuito` | si | `getImportoAnnualeAttribuito` |

**Due sistemi di naming sulla stessa riga**: `title` tecnico che e' il nome di un metodo
PHP, `txt` umano che decide la formattazione. Entrambi editabili da chi amministra i
criteri, entrambi senza guardia.

Il design proposto qui sopra li porta **dentro il trait** (`method_exists($caller, ...)`
e `Str::contains($label,'Importo')`): li promuoverebbe da difetto di una pagina a
difetto della piattaforma. **L'estrazione vale proprio perche' obbliga a sostituirli con
un contratto esplicito** — non per il DRY.

### 5. Trappola Filament da scrivere nel codice quando si implementera'

`$caller` va catturato con `use (...)`. Un parametro di closure **tipizzato con
un'interfaccia** viene risolto dal container di Filament: la closure esplode a runtime.
Lo snippet della story lo fa gia' giusto, ma senza dirne il motivo — e qualcuno lo
"migliorera'" in un parametro tipizzato.

### 6. Igiene dati

Righe di prova nella tabella criteri di IR: id 52 `ruolo`, id 54 `ssss`, entrambe con
`rule` vuota. E il gruppo `tot`/`importo *` e' ripetuto quattro volte, una per coppia
(anno, type): e' `syncRatingsWhere(['anno','type'])` che funziona, non un errore, ma va
saputo prima di contare i criteri.
